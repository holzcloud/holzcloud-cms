<objective>
The mechanical half of the standing gate, run once, after everything a person can
see has landed.

`go run ./tools/i18n` must report `0 offen, 0 verwaist` on all four catalogues it
writes. That is QUAL-01, and for this phase it is a small job with an exact
shape: **two sentences**, both added by plan 10-06, both about where the second
factor is enforced.

Two sentences is the honest size of this phase's user-visible surface and it is
worth saying why rather than letting it look like an oversight. Forward
authentication is a path a person travels without reading anything: they click a
bookmark and they are in. There is no wizard, no new screen, no new control. The
one thing that genuinely needs saying — that their second factor is somebody
else's business now — is exactly what plan 10-06 put on the account screen and on
the user list. Everything else this phase produced is read by an operator in a
terminal, in `journalctl`, in `/admin/protokoll` or in `deploy/DEPLOY.md`, and
none of those is a catalogue string.

**Why this is its own plan and not a task on the end of 10-06.** It has to run
after every user-visible change in the phase and before the browser pass, or the
browser pass reads screens in German with three empty catalogues behind them and
signs off a state that will change again. Phases 7, 8 and 9 each learned that the
same way.

Purpose: QUAL-01 for phase 10.
Output: four catalogues at zero open and zero orphaned, `de-CH.json` rebuilt, and
a recorded count that the next phase's baseline can start from.
</objective>

Four steps, in the tool's own order. Do not hand-edit a catalogue before running
the tool: `-write` adds the missing keys with empty values in the right place and
in the right order, and a hand-added key in the wrong sort position is a diff
nobody can read.

1. **`go run ./tools/i18n`** — record the count and the open keys as they stand.
   Compare against `10-06-SUMMARY.md`'s recorded list. A key open here that is
   not on that list is a string somebody minted without noticing; find it before
   translating anything, because it may belong somewhere else entirely.
2. **`go run ./tools/i18n -write`** — the four catalogues gain the new keys with
   empty values.
3. **Translate each one, in all four languages.** These are not mechanical. Both
   sentences say the same thing from two angles — one to the person it is about,
   one to the administrator looking at a list of accounts — and both hinge on a
   distinction that is easy to flatten: the second factor is not *switched off*
   here, it is *enforced elsewhere*. A translation that says "two-factor
   authentication is disabled" would be wrong and alarming; one that says "your
   organisation's sign-in handles it" is right. Keep the second person in the
   account-screen sentence and the third person in the user-list one, the way the
   German does and the way the surrounding entries in each catalogue already do.
   Follow `GLOSSARY.md` for every term it lists.
4. **`go run ./tools/i18n -schweiz`** — rebuild `de-CH.json`. The German source
   changed, so the Swiss deviations file is regenerated rather than edited.
   `fr-CH.json` and `it-CH.json` are only read by the tool; leave them alone.

Then run `go run ./tools/i18n` once more and require `0 offen, 0 verwaist` on
`en`, `es`, `fr` and `it`, and `0 ohne Gegenstück` on the three regional files.

**One thing to check by eye that the tool cannot.** The tool counts presence, not
meaning: a catalogue whose English value is the German sentence copied verbatim
reports as translated. After step 3, read the four new values in each catalogue
side by side and confirm none is the German string. Write the four sentences into
`10-09-SUMMARY.md` so the browser pass in plan 10-10 has something to compare
against a screen.
