<objective>
One display mode, six landing places, and one measured reason it cannot ride on
the field that looks like it was made for it.

**`Block.Variant` is already the gallery's column count.** `block.go:268-277`
reads it as `"2"`, empty meaning three, and `"4"`; the editor's select writes it
at `block_list.html:157-161`; `render.go` turns it into `hc-spalten-N`. Putting
a slideshow flag there would make one string mean either a number of columns or
a mode, and the first person to write `Variant = "diashow"` would get a
three-column grid with no error anywhere. So D-10's choice needs a field of its
own, and the shape for a second display axis already exists:
`internal/field/field.go:271-302` — `Def.Display`, the constant
`DisplayButtons = "knopfreihe"`, and the doc-comment rule that an empty value is
the shape that already exists.

**The other half of this plan is the arithmetic of a new `Block` field.**
`11-PATTERNS.md` §A.4 lists six places a field must land and says why they are
one commit: `internal/bundle/blocks.go` has the value written into a struct
literal on the way out (`:25-59`) and read back into another on the way in
(`:68-101`), and **a field added to one and not the other loses its value on the
round trip with nothing to say so**. Both guards are named and both are extended
here: `TestKodierenUndLesenIstVerlustfrei` for the JSON column,
`TestRoundTripKeepsBlocks` for the archive.

**And the stored value stays German.** `.planning/GLOSSARY.md`'s closing rule was
written after a runtime failure of exactly this kind: a German word standing in
the database is a value, not an identifier, and translating it in Go builds
cleanly and then fails at run time on a path no test of that phase drives. The
constant is `DisplaySlideshow`; the string it holds is German, beside
`knopfreihe`, `galerie` and the fifteen field kinds. Turning those is LANG-08's
question in Phase 12.

Purpose: GAL-06 in full.
Output: an editor picks grid or slideshow on the block, the pictures snap to
their edges, a keyboard reaches them, and nothing about it is scripted.

**The renderer, and it is deliberately almost nothing.** The gallery arm appends
the display's modifier class to the wrapper `<div>` and, when the display is the
slideshow, adds the two attributes a scrolling region needs to be reachable: a
tab stop and an accessible name. Nothing else in the markup differs between the
two modes — the tiles, the large views, the fragment ids and the controls are
all `GalleryItems`' output and identical in both. **One markup, two stylesheets**
is what makes GAL-06 "one CSS block" rather than a second renderer, and it is
what keeps the lightbox working in both modes for free.

The tab stop is not decoration. A region that scrolls horizontally and cannot be
focused is a slideshow only a pointer can use, and GAL-06 asks in as many words
for it to be reachable by keyboard. Browsers differ on whether they hand a
scroll container a tab stop on their own, so it is stated rather than assumed,
with the reason in the comment.

The accessible name goes through the translator plan 11-01 injected on the
`Set`, and it reuses the German literal that already exists as a catalogue key —
measured: it is already translated in `en`, `es`, `fr` and `it`. Marking it
costs nothing and minting a fifth string would cost four translations for a word
the catalogue already has.

**The stylesheet, one appended section, on the modifier class only.** The grid
rules at `:103-144` are untouched, and a gallery without the modifier renders
today's markup through today's rules.

The slideshow turns the same grid into a single horizontal track: the columns
flow along the inline axis instead of wrapping, the track scrolls in that axis,
and it snaps to each picture's edge. `overscroll-behavior` in the inline axis is
part of it and belongs in the comment with its reason — without it, reaching the
end of the track hands the gesture to the page behind, which on a phone is the
difference between a slideshow and an accidental navigation.

**The one thing that must be got right, and it is the finding this project has
already paid for once.** A horizontal scroll container is precisely where
`.planning/STATE.md:209` reproduces: an element that is not in the normal flow
counts toward the scroll width even when it cannot be seen, and in the `weide`
theme that made *every page of the site* scroll sideways without anyone opening
the thing that caused it. Two consequences for this section:

- the hidden large view stays hidden by removal from the layout, the way plan
  11-01's section does it, and nothing in this section changes that;
- the revealed large view inside a track must be a member of the track and not
  something placed over it — same technique, same reason.

The browser pass in plan 11-07 measures the scroll width of a page carrying a
slideshow at three widths, against the real files, the way the `weide` finding
was measured before it was believed. There is no unit test that can see this;
say so here rather than let a reader assume the suite covers it.
