<objective>
The rights, re-applied every time, and the four ways to get it wrong that all
look right.

SSO-06 asks for one behaviour and it is short to state: group membership decides
role and website access, re-applied at every sign-in so a demotion at the
identity provider takes effect here, with every change written to the activity
log. The implementation is one function. Four traps sit inside it, and three of
them pass a naive implementation's own tests.

**One: `strings.Contains`.** `X-authentik-groups` joins group names with `|`
(U+007C — from authentik's own `getHeaders` in
`internal/outpost/proxyv2/application/mode_common.go` at tags `version/2026.8.1`
and `version-2025.8`, not from a blog). Asking whether the raw header contains
`holzcloud-admins` answers yes for an account whose only group is
`not-holzcloud-admins`. Plan 10-02 wrote `Identity.HasGroup` for exactly this
reason, and this plan's job is to call it.

**Two: the empty header.** `strings.Split("", "|")` is a slice of one empty
string. A membership test against that slice makes `""` a group, and an
administration group configured as the empty string would then match everybody —
which is why `HOLZCLOUD_SSO_ADMIN_GROUP` has no default and why `splitGroups`
drops empty elements.

**Three, and this is the one neither the roadmap nor `10-CONTEXT.md` names:
D-01's inversion has a second road.** D-01 covers account *creation*: a new
account must not have zero rows in `user_websites`, because `NewWebsiteAccessLookup`
reads zero as every website. But SSO-06 says the rights are re-applied on every
sign-in, and re-applying them for an editor whose groups match no configured
website would write an **empty** assignment — arriving at exactly the same state
by subtraction. An operator removing somebody's last website group at the
identity provider, intending to take their access away, would give them access
to everything. So the sync never writes an empty website list. An editor with no
matching website group is **refused the sign-in**, which is what taking somebody's
access away should look like.

**Four: `may_publish`.** No group grants it. `SetRights` takes it as a field and
would happily overwrite it on every sign-in. It is read first and carried
through, because an operator who decided somebody submits rather than publishes
made that decision about a person, and no schedule should undo it.

Purpose: SSO-06 whole, and D-05's "no third role" as a gate rather than as a
promise.
Output: one function, one activity row per actual change, and a refusal that
closes the road D-01 left open.
</objective>

    - An account in the configured administration group signs in as `admin`; if it was `editor` before, one `user.update` activity row records the change with `from` and `to`
    - An account no longer in that group signs in as `editor`, and the demotion writes one activity row — this is the whole point of running the sync on every sign-in

    - An editor whose groups map to **no** configured website is refused: no session, one `auth.login_fail` row naming the reason, fall through to the password form, and — asserted explicitly — their existing `user_websites` rows are **unchanged**, because a refusal must not be a way of emptying an assignment
    - An administrator's `user_websites` rows are left exactly as they are: `Rights` returns `Everything()` for an administrator before reading them, so writing there would be a change with no effect and a diff with no reason
    - `may_publish` false before the sign-in is false after it
    - Two consecutive sign-ins with unchanged groups leave identical rows and write exactly **one** activity row in total — the first one, from whatever changed then
    - An account that is the last administrator and is no longer in the administration group keeps `admin`, the `Update` refusal is logged at warn level naming the account, and the sign-in continues
    - An identity with an empty `X-authentik-groups` header has no groups: not one group named the empty string

pre-existing one alike — and **before** `RenewToken` and `completeLogin`, so the
role that reaches the session is the synced one and not the stale one.

    func (h *Handler) syncRightsFromGroups(ctx context.Context, r *http.Request,

Its returned `role` is what `completeLogin` is handed. Its `err` is a refused

**The role.**

    want := user.RoleEditor
    if h.cfg.SSOAdminGroup != "" && ident.HasGroup(h.cfg.SSOAdminGroup) {
        want = user.RoleAdmin
    }

Two comments belong here and both are short. The first names the trap:
`ident.HasGroup` compares whole elements of the pipe-separated header, and
`strings.Contains(raw, "holzcloud-admins")` — the obvious version — is true for
`not-holzcloud-admins`. The second names D-05: `want` is one of exactly two
values because `00001:7` carries a table-level
`CHECK (role IN ('admin','editor'))`, and loosening a table-head CHECK in SQLite
means rebuilding a table that has foreign-key children. There is no third role
and this is not the phase that invents one.

When `want != u.Role`, call `h.users.Update(ctx, u.ID, u.Name, u.Email, want)`.
Handle its last-administrator refusal explicitly: recognise the error, log
`slog.Warn` naming the account and the fact that the identity provider asked for
a demotion the installation cannot perform, keep `u.Role`, and continue. Do not
treat it as a database failure and do not fail the sign-in — locking the last
administrator out because a group changed is a worse outcome than a role that
lags one commit behind.

On a real change, write one `activity.Entry` with
`Action: activity.ActionUserUpdate`, `EntityType: "user"`, `EntityID: u.ID`,
`ActorEmail: u.Email` and
`Metadata: map[string]any{"field": "role", "from": u.Role, "to": want, "via": "sso"}`.
Use the existing action constant; `entry.go:40-46` says why a new one would make
older rows unfindable and why metadata is free.

**The websites.**

If `want == user.RoleAdmin`, return without touching `user_websites` at all, with
a comment saying why: `user.Store.Rights` returns `Everything()` for an
administrator two statements before it reads that table (`rights.go:64-66`), so
anything written there is invisible — and an invisible write is a diff a later
reader has to reason about for nothing.

Otherwise, collect the ids: for each group the identity carries, look it up in
`h.cfg.SSOWebsiteGroups`; ignore a group that is not there (an identity provider
has groups this installation has never heard of, and that is normal, not an
error). Deduplicate and sort — `SetRights` does both again, and doing it here as
well is what makes the comparison below reliable.

**Then the refusal.** If the resulting slice is **empty**, return an error that
`ForwardAuthSignIn` turns into `refuseSSO` plus a fall-through. Write the longest
comment in the function above it:

> An empty assignment is not "no websites". `NewWebsiteAccessLookup` (`internal/admin/handler.go`)
> reads `assigned == 0` as **every** website, and it is right to — see
> `internal/user/rights.go:9-22`. D-01 closes that road for account *creation*;
> this is the same door reached from the other side, because SSO-06 re-applies
> the rights on every sign-in. An operator who removes somebody's last website
> group at the identity provider means to take their access away, and writing
> an empty list would hand them everything. So nothing is written and the
> sign-in is refused.

Assert in the test that the existing rows survive that refusal. A refusal that
also empties the assignment would be the bug wearing a different hat.

Otherwise: read the current rights with `h.users.Rights(ctx, u.ID)`, compare the
website sets, and call
`h.users.SetRights(ctx, u.ID, user.Rights{MayPublish: current.MayPublish, Websites: ids})`
only when they differ. `MayPublish` is carried through and never derived — no
group grants it, and an operator's decision about a person must not be reset on
a schedule. On a change, write one `activity.Entry` in the same shape as the
role one, with `"field": "websites"` and the two sorted lists as `from` and
`to`.

Calling `SetRights` only on a difference is what keeps `/admin/protokoll`
readable: `SetRights` is idempotent, so calling it every time would be harmless
and logging every time would not.

Extend `forwardauth_test.go` with one named English subtest per line of the
