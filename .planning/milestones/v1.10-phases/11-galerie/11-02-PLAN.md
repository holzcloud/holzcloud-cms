<objective>
The table and the store, built alone and proved alone, with the one design
question in this phase that has a documented body count.

`11-PATTERNS.md` §C.2 puts two analogs side by side and they disagree.
`internal/menu/store.go` has the ordering this album needs — `SwapSortOrder`,
two rows, one transaction — and the wrong scoping: `GetMenu`, `UpdateMenu`,
`DeleteMenu`, `DeleteItem` all take a bare primary key and will happily read or
write a row belonging to any website. `internal/term/store.go` has the right
scoping — `website_id` in every WHERE, `RowsAffected() == 0` turned into a named
error — and no ordering at all.

**This is not a style preference, and the store's own doc comment says so.**
`internal/menu/store.go:14-33` records what the bare-key shape cost: on
2026-09-06 four menu-item handlers reached another website's navigation because
nothing in a signature made the caller supply the website, so nothing reminded
them. `de4a1ce` is the commit that proves it and `5e453a9` the one that fixes
it. GAL-05 asks that an album be *invisible from every other website*; a store
whose `Delete` takes no `websiteID` cannot make that a fact of the database, and
this phase adds nine handlers.

So: term-shaped signatures, menu-shaped ordering, and the item statements scoped
through a subquery on `albums` because `album_items` has no `website_id` of its
own — which is the exact reason the menu store gives for not having been fixed
that way already, and the reason to pay it here while the table is new.

Purpose: GAL-05 in the database rather than in a convention, the storage half of
GAL-03, and the list GAL-07 says both the block and the album must share.
Output: `internal/db/migrations/00050_albums.sql` and `internal/album`, provable
against a real SQLite file and with no HTTP anywhere near it.
</objective>

Create `internal/album`, a new package. Two files plus its test.

**`album.go` — the model and the two bounds.**

`Album{ID, WebsiteID int64; Slug, Name string; CreatedAt time.Time}` and the
picture row. The picture row is where GAL-07 is decided: it carries an id, an
album id, a sort order and — for the three content fields — **the same three
`block.Item` carries**. Expose the list to callers as `[]block.Item` so the
album feeds the *same* type into the *same* renderer that plan 11-01 exported;
a parallel type with the same three fields would be a second shape and the
beginning of a second renderer. Say that in the doc comment, and name
`block.Item` in it.

Two bounds, each a named constant with a two-sentence reason above it in the
register of `internal/block/block.go:165-175`:

- `MaxNameLength = 60` — the same as a label's, and for the same reason: a name
  is a heading in a list, not a paragraph.
- `MaxItems` — an album is a *reusable* set and may legitimately be larger than
  the 24 a single block is capped at, but it is expanded into a page on every
  request that names it, so it needs a ceiling of its own. Pick one, state it,
  and say what goes wrong without it: an unbounded album is an unbounded page,
  built on the read path, for anybody who asks. **Reported and not silently
  applied** — `AddItem` past the cap returns a named error rather than dropping
  the picture, which is the discipline `wxr.Export.Truncated` sets for the whole
  repository.

**`store.go` — the package doc comment first, and it is the load-bearing part.**
Two paragraphs. The first says what this store enforces and where the shape came
from: `website_id` in the WHERE clause of every statement and
`RowsAffected() == 0` as a named error, taken from `internal/term/store.go:284-311`
and **not** from `internal/menu/store.go`, whose own doc comment at `:14-33`
records what the bare-key shape cost on 2026-09-06 — four handlers reaching
another website's navigation because nothing in a signature made anyone supply
the website. `album_items` has no `website_id` column, exactly as `menu_items`
has none, and that is precisely the reason the menu store gives for not having
been fixed; here it is paid while the table is new, with a subquery on `albums`
in every item statement.

The second paragraph quotes `internal/term/store.go:318-328`'s warning and says
it applies here word for word: two callers that derive a slug with two different
calls create a second row beside the one they meant to reuse. **This store makes
exactly one call to `page.Slugify` and everything else goes through it** — the
bundle importer in plan 11-06 will call `Create`, not its own derivation.

Details that are decisions rather than typing:

- **`Create`** normalises the name the way `term.Normalize` does — collapse
  runs of whitespace, refuse the empty result, cut at `MaxNameLength` — then
  derives the slug with `page.Slugify` and inserts. A UNIQUE violation becomes a
  **named exported error** so the handler in plan 11-03 can say "an album with
  this name already exists" instead of `strings.Contains(err.Error(), "UNIQUE
  constraint")`, which is what `internal/admin/menu.go:172` has to do today.
  Note in the comment that `page.Slugify` returns `untitled` rather than an
  empty string, so two albums named only in punctuation collide on the
  constraint rather than producing an empty key — which is why the collision
  needs a name at all.
- **`Get` and `BySlug`** return `(nil, nil)` on `sql.ErrNoRows`, as
  `menu.GetMenu` does. Not found is not an error; it is a 404 at the handler.
- **`Rename`** moves `name` and leaves `slug` alone, with the sentence
  `term.Rename` already carries: the slug is what pages point at, and correcting
  a typo must not break every page that carries the album. This is the method
  GAL-04's test cannot exist without, and plan 11-06 depends on it.
- **`Delete`** errors on `RowsAffected() == 0`. This is deliberately stricter
  than `term.Delete`, which does not — a delete that silently does nothing
  because the album belongs to somebody else is the exact failure GAL-05 is
  about. Say in one line that it is stricter and why.
- **The four item methods** reach the website through a subquery:
  `… WHERE id = $1 AND album_id IN (SELECT id FROM albums WHERE id = $2 AND
  website_id = $3)`. Zero affected rows is an error in each. Write the subquery
  once as a documented SQL fragment constant, or write it four times and say in
  the comment that four copies of one clause were preferred to a builder — but
  do not leave a reader guessing which was meant.
- **`SwapSortOrder`** is `internal/menu/store.go:196-222` with the scoping
  added: `BeginTx`, `defer tx.Rollback()`, read both orders **through the
  scoped subquery** so an item of another website's album never even yields a
  number, write them crossed, `return tx.Commit()`. Nothing between the two
  reads and the two writes touches the network, the filesystem or user input;
  say so in the comment, because the write pool admits exactly one connection
  and a transaction that waited on anything would block every request on the
  machine.
