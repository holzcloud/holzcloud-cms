# Milestone audit: v0.1.0 — Betrieb härten

This audit was written after the release, on 2026-10-26. v0.1.0 was released on
2026-10-18 as 0.1.0, the first beta, without one. It rests on the records the
milestone left behind: the four VERIFICATION files of phases 20 to 23, the UAT of
phase 23, the 0.1.0 entry of `CHANGELOG.md`, `docs/beta.md` and the release
page. It checks nothing that was not already checked there; where a record is
uneven, this audit says so and does not smooth it.

Opened 2026-10-12. Four phases (20 to 23), eighteen plans, thirteen requirements.
All thirteen are marked `[x]` and Complete in `v0.1.0-REQUIREMENTS.md`, and each
phase's VERIFICATION file carries `status: passed`.

The milestone asked for one thing: that holzcloud-cms runs demonstrably safely in
operation and closes as release 0.1.0, the first beta. The test environment was
decided on 2026-10-12: no real server, a Linux container with systemd, with every
difference from a real server named next to the measurement.

How to read the Record lines: each requirement below ends with one line that
starts with `Record:`, names the file it rests on and quotes one sentence from
it, copied byte for byte. `27-check.sh archive audit` finds each of them with
`grep -F` in the file it names.

## Where the record is uneven

Three facts, stated as facts. The first two are in the records and in the
release notes; the third is a difference between a UAT entry and the remote,
measured on the day this audit was written.

**The hardened unit ran under systemd 252 in a container, not on a real server.**
`docs/beta.md` opens with it: every row was shown in a Debian 12 container with
systemd as PID 1, amd64 under emulation on an arm64 host, except where a row says
otherwise, and no row is about a real server. On the emulated platform the first
start crashed and needed a drop-in that exists only in the container; native
arm64 started the unit unchanged.

**The plugins were measured on native arm64 only, not on amd64.** The verdict on
`MemoryDenyWriteExecute` is SETTLED on arm64 and VOID on amd64, because the
seccomp directives are not enforced under the amd64 emulation. The target
platform of the program is linux/amd64. Both this and the container point above
are in the 0.1.0 release notes (the CHANGELOG entry) and in `docs/beta.md`. As
released, `docs/beta.md` says no native amd64 run was made and none was planned;
milestone v0.1.1, opened on 2026-10-20, takes both up.

**The UAT of phase 23 records a branch deletion as passed that had not happened.**
Test 2, "Branch deletion (optional follow-through)", is recorded as `result: pass`
with no evidence line. It concerns nine branches: the seven rated Safe to delete
in `docs/branches.md`, and `backfill-releases` and `tagfix`, which were to be
decided first. `git ls-remote --heads origin`, run on 2026-10-26, still lists all
nine: `backfill-releases`, `claude/holzcloud-projects-update-0t9epb`,
`claude/project-open-tasks-lwuj02`, `claude/task-phases-milestones-open-mt1qz0`,
`feat/holzwave-farben`, `fix/tables-mobile`, `holzbar-colours`,
`redirects-keep-language` and `tagfix`. The `pass` was recorded for a step that
the verification file itself calls optional follow-through and that REPO-03 does
not require, but it reads as done and was not. Phase 27 (TIDY-01) takes it up.

Record: `.planning/milestones/v0.1.0-phases/23-repository-tidy-and-beta-criteria/23-UAT.md` — "Seven Safe-to-delete branches removed via GitHub UI per docs/branches.md; backfill-releases and tagfix decided first."

## What was deliberately not done

Taken from the records, not added to them.

- **No real server.** Decided on 2026-10-12 and kept as an Out of Scope row in
  the requirements: no test on a real server, a container with named differences
  in its place.
- **No new features** in the administration or the themes. The milestone hardens
  operation and builds nothing an operator sees in a menu.
- **No automatic deletion of the orphaned branches.** The proxy refused ref
  deletion; the GitHub interface was the route.
- **No high availability, replication or off-site backup service.**
- **Not exercised, and named as such in `docs/beta.md`:** the real 03:15 timer
  window, `Persistent=true`, `RandomizedDelaySec`, the `REMOTE_TARGET` copy,
  retention pruning, native amd64 timing, a restore on a real server.
- **Nine review warnings of phase 22** about the failure paths of `backup.sh`
  and `restore.sh` were left as advice by the phase 22 VERIFICATION; none
  contradicts a must-have.
