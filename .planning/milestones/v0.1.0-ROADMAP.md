# Roadmap: holzcloud-CMS, v0.1.0 (Betrieb härten)

The phase 20 to 23 detail and the Progress rows 1 to 23 below were moved here from `.planning/ROADMAP.md` on 2026-10-26, at commit 3b06411496, without a word changed. v0.1.0 opened on 2026-10-12 and was released on 2026-10-18 as 0.1.0, the first beta. Its requirements are in `v0.1.0-REQUIREMENTS.md` and its audit, written after the release, in `v0.1.0-MILESTONE-AUDIT.md`.

## Phases

### Phase 20: Hardened unit under real systemd

**Goal**: The hardened `holzcloud.service` is proven to run, plugins included, under a real systemd.
**Requirements**: UNIT-01, UNIT-02, UNIT-03
**Success Criteria**:
  1. The unit starts in a systemd container and the site answers HTTP.
  2. Every shipped wasm plugin loads under the unit; the `MemoryDenyWriteExecute` vs. wazero question is settled with evidence and the unit adjusted if needed.
  3. `systemd-analyze security` score is measured and committed; container-vs-server differences are named.

**Note**: Hand the test container recipe to later phases; 21 and 22 reuse it.
**Plans**: 3/3 plans complete in 3 waves

Plans:
**Wave 1**
- [x] 20-01-PLAN.md — Container recipe in `deploy/test/` and UNIT-01: the unchanged unit starts under real systemd and `/healthz` answers; enforcement canary tells whether seccomp is real

**Wave 2** *(blocked on Wave 1 completion)*
- [x] 20-02-PLAN.md — UNIT-02: seed five plugins through `/ai`, check loaded/running/invoked and the wazero engine, `MemoryDenyWriteExecute=no` control, verdict, comment in the unit; one narrow native arm64 run (named deviation from D-01)

**Wave 3** *(blocked on Wave 2 completion)*
- [x] 20-03-PLAN.md — UNIT-03: raw `systemd-analyze security` score, `deploy/SECURITY-SCORE.md` with container-vs-server differences, `deploy/test/README.md` hand-over to phases 21 and 22

### Phase 21: Deploy, update, rollback

**Goal**: Install, update and rollback are played through and the docs match what happened.
**Requirements**: DEP-01, DEP-02, DEP-03
**Depends on**: Phase 20
**Success Criteria**:
  1. A fresh install by `deploy/DEPLOY.md` alone works; every deviation found is fixed in the doc.
  2. An update across at least one migration keeps all data.
  3. A rollback is played and documented, with the migration limit stated.

**Plans**: 6/6 plans complete in 6 waves

Plans:
**Wave 1**
- [x] 21-01-PLAN.md — Harness core (`doc_play` reads the commands out of DEPLOY.md and refuses a line it does not contain) and the unedited document played from `systemd-base`: install, First Run over curl, Caddy validation, Backups block; raw pass-1 evidence (DEP-01)

**Wave 2** *(blocked on Wave 1 completion)*
- [x] 21-02-PLAN.md — DEP-01 repaired from the evidence (Prerequisites, Build stamping, Install paths, First Run, Caddy), `deploy/DEPLOY-RUN.md` created, pass 2 clean; old-version install seeded (v0.0.10) and the Updating section played as shipped (DEP-01, DEP-02)

**Wave 3** *(blocked on Wave 2 completion)*
- [x] 21-03-PLAN.md — DEP-02: no-data-loss proof (state before/after, content hashes, ATTACH against the pre-upgrade snapshot), Updating section rewritten (back-up first, kept old binary, snapshot facts, journal check) and replayed

**Wave 4** *(blocked on Wave 3 completion)*
- [x] 21-04-PLAN.md — DEP-03: snapshot rollback played, negative case (old binary on migrated database), "Rolling back" section with the migration limit first, Recovery text cross-linked

### Phase 22: Backup and restore, measured

**Goal**: A backup that has been restored is the only backup; prove it.
**Requirements**: BAK-01, BAK-02, BAK-03
**Depends on**: Phase 20
**Success Criteria**:
  1. `backup.sh` output passes its integrity check and contains database and media.
  2. `restore.sh` onto an empty system yields working pages, media and login; time and size recorded.
  3. One run through `holzcloud-backup.timer` is observed.

**Plans**: 5/5 plans complete in 5 waves

Plans:
**Wave 1**
- [x] 22-01-PLAN.md — Harness tracer and proof (two containers, `backup`, `transfer`, `restore`): the document's backup line, a tar stream, the document's restore line answered `yes`, a login; then two integrity readers, whole-directory content comparison, cross-container state comparison, timing and size, each able to fail (BAK-01, BAK-02)

**Wave 2** *(blocked on Wave 1 completion)*
- [x] 22-02-PLAN.md — `backup-timer` (container-only drop-in, one observed run of the hardened service), `restore-negative`, `backup-fixture` (planted directories, 300 MiB bulk media), `backup-chain` with a fixed summary vocabulary, README (BAK-01, BAK-02, BAK-03)

**Wave 3** *(blocked on Wave 2 completion)*
- [x] 22-03-PLAN.md — Pass 1: the unchanged scripts and document played end to end at two data points; `22-FINDINGS.md` with every difference, the D-16 candidates, settled assumptions and the numbers (BAK-01, BAK-02, BAK-03)

**Wave 4** *(blocked on Wave 3 completion)*
- [x] 22-04-PLAN.md — Repair from the findings (`backup.sh` and `restore.sh` carry plugins, language files and logo), DEPLOY.md Backups and Restore corrected, the two docs aligned, the final evidence set from fresh containers (BAK-01, BAK-02, BAK-03)

**Wave 5** *(blocked on Wave 4 completion)*
- [x] 22-05-PLAN.md — `deploy/BACKUP-RUN.md` from the final set with a byte-for-byte proof of the appendix, README hand-over to phase 23, repository gates (BAK-01, BAK-02, BAK-03)

### Phase 23: Repository tidy and beta criteria

**Goal**: 0.1.0 says what it promises and the repository carries nothing stray.
**Requirements**: REPO-01, REPO-02, REPO-03, QUAL-01
**Depends on**: Phases 20–22
**Success Criteria**:
  1. Beta criteria are written down.
  2. CHANGELOG and release notes for 0.1.0 exist and the tag is set.
  3. Orphan branches are listed with GitHub-UI deletion steps.
  4. `go run ./tools/i18n` reports `0 open, 0 orphaned`.

**Plans**: 4/4 plans executed in 3 waves

Plans:
**Wave 1**
- [x] 23-01-PLAN.md — Tracer and beta criteria: level with origin/main, i18n baseline, one promise from its record to release.yml's input (heading `## 0.1.0`), then `docs/beta.md` complete: ten cited promises, the non-promises, the evidence binding, the note on the word alpha (REPO-01, REPO-02, QUAL-01)

**Wave 2** *(blocked on Wave 1 completion)*
- [x] 23-02-PLAN.md — The 0.1.0 CHANGELOG entry in German with the upgrade note for operators on 0.0.25, README badge and notice, the Versioning section of `docs/deployment.md` (REPO-02, REPO-01)
- [x] 23-03-PLAN.md — `docs/branches.md`: the remote branches generated from git with evidence-based verdicts, GitHub-UI deletion steps, restore routes, the two branches that carry push-triggered workflows (REPO-03)

**Wave 3** *(blocked on Wave 2 completion)*
- [x] 23-04-PLAN.md — The owner's steps (push `main`, push `main:release`, tidy the branches) with the veto points, and every gate run once more on the end state (REPO-02, REPO-03, QUAL-01)
