<objective>
Build the first end-to-end path of the backup proof in the Phase 20/21 harness: a backup made by the document's own line in a populated source container, carried to a fresh target container, restored there by `restore.sh` with the answer `yes`, and shown to give a logging-in system; then turn that path into a proof by adding the whole-directory content comparison, the second integrity reader, the cross-container state comparison, the measurements and the permission checks, each able to fail (BAK-01, BAK-02).

Purpose: ROADMAP says a backup that has been restored is the only backup. The harness must be able to say, from two different containers and without leaning on state that survived in place, whether the restored site is the backed-up site. Plans 22-02 to 22-05 extend this vocabulary and must not have to rename it.

Output: run.sh subcommands `backup`, `transfer`, `restore`; the helpers `on_target`, `backup_verify`, `tree_hash`, the tree and row comparisons with their selftests; two additions to `doc_cmd`; scratch evidence under deploy/test/out/ for plans 22-02 and 22-03.

Schema gate: no database schema or migration is touched; the service migrates by itself at start, as in Phase 21.

A comparison that cannot fail proves nothing: every comparison below has a selftest and every failing assertion is a BAD line that is written before the subcommand exits 1.

(1) `tree_hash DIR`, run in the current container as root: one line per regular file below DIR, the sha256 and the path relative to DIR, sorted by path, with GNU find, sort -z and xargs -0 inside the container; the output is a host file. The exclusions live in one place as a named list and each is written to the verify file as an INFO line `EXCLUDED pattern: reason`: the SQLite family `holzcloud.sqlite*` (compared by integrity and row counts, because the snapshot is a different file by design), `pre-upgrade-*.sqlite` (old-schema copies the service writes before a migration, deliberately not backed up), the readiness probe file the service writes into the data directory, and MANIFEST (only a backup has one). Before settling the list, list the real source data directory once (`find /opt/holzcloud/data -maxdepth 2`) and name any other file or directory that is not in the backup as a finding in the BAD lines instead of excluding it: an exclusion is a decision with a reason, never a convenience. Files and directories that the backup is expected to hold but does not (the plugin tree, the language and logo directories) must surface as BAD, which is the point of the whole-directory scope: a comparison limited to the directories the script copies would pass while the restore is broken (D-07).

(2) `tree_compare LISTA LISTB LABEL`, on two host files with POSIX awk and sort only (the host is macOS): PASS `tree LABEL: N files equal`, or one BAD per path (`tree LABEL: only in A: path`, `only in B: path`, `differs: path`). It asserts the first list is non-empty and that at least one path below `./media/` is in it: an empty media directory would pass a listing and must fail here (D-07). `tree_selftest`: take a copy of the source list, drop one line and change one hash, run the comparison on it, require a BAD for each; run it once on an empty list and require a BAD for non-empty; write all of that, including the expected BAD lines, to OUT_DIR/selftest-tree.txt (never into verify-backup.txt) and end the file with `SELFTEST OK`; die if a tampered input was accepted.

(3) `rows_compare DB STATEFILE LABEL`: for every table in sqlite_master of the backup database, read through the immutable URI, count the rows (counts only, never a row of any table: users, sessions and key tables included), compare with the `table NAME N` lines of the state file using the existing st_count and is_volatile, PASS `rows T`, INFO for volatile tables, BAD for a difference or for a table that exists on one side only. Write the raw counts to OUT_DIR/rows-LABEL.txt.

Sizes and counts go to OUT_DIR/LABEL.txt as KEY lines: `BYTES:` (du -sb of DIR; the comment says du -sb counts apparent bytes and each directory as 4096), `SIZE:` (du -sh), `DB-BYTES:`, `MEDIA-BYTES:`, `FILES:`, `MEDIA-FILES:`, `HOST-ARCH:` (docker info Architecture) and `CONTAINER-ARCH:` (uname -m in the container), so the record can say these are emulation numbers (D-14, D-15). Add `MEDIA-SERVED:`: the sha256 and HTTP status of `GET /media/WEBSITE/FILENAME` with Host test.local, the website id and file name taken read-only from the first row of the media table (the same row STATE_SH reads), plus an INFO line saying whether it equals the staged source image.
