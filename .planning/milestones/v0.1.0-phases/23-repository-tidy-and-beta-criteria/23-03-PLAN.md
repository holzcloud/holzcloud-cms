`## Deleting a branch in the GitHub UI` (D-16). Numbered steps, for the owner, in this order: open the repository on GitHub; open the branch dropdown above the file list and choose View all branches (the Branches page, which is also reached under Code); find the branch in the list; click the trash icon at the end of its row and confirm if GitHub asks. Then the second route for a branch whose pull request is closed or merged: open the repository's Pull requests, click Closed, open the pull request, and click Delete branch near the bottom; the button is not shown while an open pull request exists for the branch. Run `gh pr list --state open` first and state in the page whether any open pull request exists (at research time there was none); deleting the head branch of an open pull request closes it. Then three cautions: `release` is Keep and is not deleted, because it is the button of the release workflow; each `claude/` branch is deleted only after the owner has checked that no session is working on it; and the two Review first branches are looked at before anything is deleted (next section but one).

`## Restoring a deleted branch` (D-16, research assumptions A1 and A2). Say first that the table's Tip column is what makes a deletion recoverable. Route A, for a branch that had a pull request: before writing it, read GitHub's article `Deleting and restoring branches in a pull request` at https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-branches-in-your-repository/deleting-and-restoring-branches-in-a-pull-request (the docs.github.com address that was checked on 2026-10-14; a fetch of the older address under pull-requests answered 404). The article says to open the closed pull request and click Restore branch near the bottom of it. Write the route as the article words it, cite the address, and say that it was read on the date you read it; if the article cannot be fetched, write the route as `unverified` and say why. Do not claim more than the article states: it names closed pull requests, and whether a merged one offers the same button is not stated in the part that was read. Route B, for every branch, including those that never had a pull request (read the PR column to name them: they have no Restore button): recreate the branch from the Tip SHA with `git push origin SHA:refs/heads/NAME` from any clone that still holds the commit. Mark Route B with the word `unverified`: how long GitHub keeps a commit that no branch reaches any more is not documented, so the Tip SHA restores the branch only as long as the commit is still available.

`## Branches to look at first`: one subsection per Review first branch of the table, generated from the table and not from memory. Say that the workflow runs on the next push to that branch and that deleting the branch removes the trigger together with the unmerged commit, and say plainly that the owner decides, because the commits are not in main and Claude does not decide on unmerged work (D-15). End the page with one line saying which commands regenerate the table and that this page was written without deleting, pushing or tagging anything.
