## Was jeder Befund behauptet

### 1. field.Check has no arm for janein at all — a stored "nein" resolves to true and every shipped theme prints "ja"

`internal/field/field.go:753` · medium · D-false-distinction · **offen**

The switch in Check (field.go:753-856) has a case for every kind that can be got wrong except KindBool. Any non-empty string passes, and Resolve then reads everything that is not "0" as yes.

**Was passiert:** An operator restores a website archive (or asks the assistant) with `{"werte":{"im_angebot":"nein"}}`. field.Clean keeps it (non-empty), field.CheckAll returns no reason, it is stored. field.Resolve yields true, field.List sets `.Yes`, and the public page prints "Im Angebot: ja" for a page whose data says the opposite. Nothing is logged. The same value round-trips through the admin form as a ticked box, so re-saving makes the lie permanent.

### 2. bereich: NaN passes both bounds, so a range field's whole point is bypassable

`internal/field/field.go:772` · medium · other · **offen**

ParseNumber accepts "NaN" (and "Inf"), and the bounds test is a pair of ordinary float comparisons, both of which are false for NaN. A `bereich` declared 2..12 accepts "NaN" as an in-range value.

**Was passiert:** A spreadsheet column feeding a `Sitzplätze` field bounded 2..12 contains the cell `NaN` (Excel writes this for a division error). The dry run reports the row as creatable, the import creates the page, and the public page prints "Sitzplätze = NaN". The one guarantee the kind exists to make — "eine Zahl zwischen zwei Grenzen" (field.go:73) — is not made, and the operator was told on the mapping screen that the row was fine.

### 3. Phase 8's snippet-field import warnings are German fmt.Sprintf strings printed raw on an admin screen

`internal/bundle/import.go:896` · medium · C-i18n · **offen**

Defect family C, a third live instance beside internal/admin/wordpress.go:68-84 and internal/field's rejection reasons. Phase 8 added four operator-facing sentences to the import report, all built with fmt.Sprintf and all hard-coded German. import_report.html renders every other string through {{t}}/{{tf}} but prints the warning list verbatim, so an admin working in en/fr/it/es gets German. tools/i18n collects only template {{t}}/{{th}}/{{tf}} literals and the first string argument of eight named Go functions (tools/i18n/main.go:52-65) — none of these four goes through any of them, so the milestone gate's `go run ./tools/i18n` reports these strings as neither offen nor verwaist: the tool cannot see them at all.

**Was passiert:** An operator whose admin language is English imports an archive whose snippet carries a picture field. The page they land on says "Import abgeschlossen" / "What did not come along" in English, and under it a German sentence beginning "Textbaustein \"footer-kontakt\": die Werte von bild zeigen auf Nummern der Anlage…" — the one line on the screen that actually tells them something went wrong is the one line they may not be able to read. The i18n gate stays green because the collector never sees the string.

### 4. A blank Schlagwörter cell wipes an updated page's terms

`internal/csvimport/row.go:735` · high · D-false-distinction · **offen**

`Writer.setTerms` decides "did the file say anything about terms" per FILE (is a terms column mapped at all) while `Writer.update` decides the same question per ROW (`cellFor(row, m, t) != ""`). A row whose Schlagwörter cell is blank therefore reaches `term.Store.SetForPage` with an empty name list, and SetForPage's first statement is an unconditional `DELETE FROM page_terms WHERE page_id = $1`. This is precisely the distinction `update`'s own doc comment says cannot be drawn: "a blank cell is exactly as much 'empty now' as it is 'not filled in', the data does not carry the difference, and code that claims to read it is reading something that is not there."

**Was passiert:** Website with 300 published pages, each carrying tags an editor set by hand. Operator exports titles and bodies to a spreadsheet, adds a Schlagwörter column, fills it in for the 20 rows they care about and leaves the other 280 blank, then imports with target=bestehend and collision=aktualisieren. AutoMap points the column at `terms` ("schlagwoerter" is in fixedSpellings, mapping.go:322). Every one of the 280 blank rows calls SetForPage with an empty list, so all 280 pages lose every tag. The dry run says nothing about terms on updated pages, the report says "280 aktualisiert" with no group line, and page_terms is not part of a page revision — so nothing on screen mentions it and nothing can undo it.

### 5. The importer's address lookup ignores the page's language

`internal/admin/csvimport.go:979` · high · A-scope · **behoben (vorher)**

`csvRun` decides create-vs-update with `h.pages.GetPageBySlug(ctx, websiteID, slug)`, whose own doc comment says it "answers for whichever of them the database hands back first, which is right for 'does this address exist at all' and wrong for 'which page is this'" — and the importer uses it for exactly the second question, then hands the row it got to `UpdatePage(existing.ID, …)`. Since migration 00045 the constraint is UNIQUE(website_id, locale, slug), the admin deliberately proposes the SAME address for a translation, and `CheckRow` never sets `PageCreate.Locale`, so every imported page is created in the main language ('') while the collision check is language-blind. The scope the importer enforces is the website; the scope the address actually lives in is (website, locale).

**Was passiert:** Website with main language de and extra locale fr. `/kontakt` exists as a French page (locale 'fr'); the German one has not been written yet, so (website, '', 'kontakt') is free. CSV import into that website, one row with slug `kontakt`. With collision=uebergehen the row is reported "Unter „kontakt" gibt es die Seite schon. Sie wurde nicht angerührt." and the German page is never created, although its address is free. With collision=aktualisieren it is worse: UpdatePage is called on the French page's id, so the German title, Markdown, HTML and status are written into the French page (which keeps locale='fr'), a revision is recorded, and the report reads "1 aktualisiert". The same happens for any slug shared across languages whose translation row is older than the original — GetPageBySlug pins no ordering at all.

### 21. Bundle import re-derives a block kind's key from its name and ignores the key the archive carries, so a renamed kind loses every block on every imported page

`internal/bundle/import.go:410` · medium · other · **offen**

The manifest exports a block kind's stable key — `Key string `json:"key"`` at bundle/format.go:89 — and the struct's own doc comment says why: "The kind has to travel with the blocks that use it: without it, an imported page would carry pieces of a type nothing on the other side has heard of, and Clean would drop every one of them" (format.go:85-87). importBlockTypes throws that key away: it calls `s.BlockTypes.Create(ctx, websiteID, t.Name, t.Hint)` (import.go:410), and Create derives the key with `field.SlugifyKey(name)` (block/store.go:123). The key and the name are decoupled on purpose — block.Store.Update changes only name and hint, and says so: "The key is not among them: it stands in every block of that kind on every page and in the CSS class the theme styles" (block/store.go:157-160). So after any rename the exported Key and SlugifyKey(Name) differ, the import mints a different key, and the blocks that travelled with `Type` set to the old key (bundle/blocks.go:72) meet a Set that has never heard of it. Migration 00050 warns against precisely this move for albums: "a rename must move the name and NOT the slug ... would otherwise take the album away from every page that carries it, silently, at the moment of the correction" (00050_albums.sql, slug/name comment).

**Was passiert:** A site defines a block kind "Rezeptschritt" (key rezeptschritt), uses it on forty recipe pages, then an editor renames it to "Arbeitsschritt" — an act block.Store.Update documents as safe because the key does not move. The site is exported and imported onto a second installation. importBlockTypes creates a kind with key "arbeitsschritt"; the forty pages arrive carrying blocks of type "rezeptschritt"; set.Clean drops all of them; block.PlainText and block.Render then run over what is left, so the markdown column and the rendered HTML are rebuilt without the recipe steps as well. The import report lists only missing image files. Note that internal/bundle/blocks.go is being edited by another agent right now (it gained Block.Display in 6779fad), but exportBlocks/importBlocks and this Create call predate that work.

### 25. pages.list hands public plugins scheduled, expired and password-protected pages

`internal/public/pluginhost.go:99` · high · A-scope · **behoben (heute)**

The plugin host's `pages.list` operation is the one public read of pages that does not go through `page.ListablePredicate`. ### 26. pages.get returns a password-protected page's full body to a plugin with no password check

`internal/public/pluginhost.go:70` · medium · A-scope · **offen**
