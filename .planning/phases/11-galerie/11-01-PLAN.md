<objective>
The thinnest path that touches every layer the phase will modify, wired
end-to-end: a picture in a gallery, a large view of it, a stylesheet that
reveals it, and a specification that tells a theme author to load that
stylesheet. One vertical slice, production quality, and every later plan builds
out from it.

**Why this is the tracer and not a layer.** The lightbox is the one shape in
this phase with **no analog anywhere in the tree** — `11-PATTERNS.md`'s "No
Analog Found" table says it in as many words: grepping `bausteine.css` and
`admin.css` finds no `:target` rule at all. Everything else in Phase 11 is a
copy of something (`menus` for the table, `term/store.go` for the scoping,
`snippet.Expand` for the late binding, `bundle_test.go:1138` for the round-trip
test). If the markup shape is wrong, it is wrong here, on the phase's best
early-context tokens, after one commit — not after the album, the admin area
and the bundle have all been built on top of it.

**The finding that constrains the markup, and it is a measurement rather than a
taste.** A `:target` lightbox does not degrade, it fails: without its stylesheet
the large view is either always visible — every picture rendered twice, at full
size, on every page — or the anchor does nothing at all. All eight shipped
themes link `/assets/bausteine.css` from their `layout.html`;
`internal/tmplspec/TEMPLATE-SPEC.md` mentions it **nowhere**, verified by grep,
count zero. So a theme written by following the specification renders a gallery
unstyled today, and would render a lightbox broken tomorrow. This plan ships
both halves of D-01: the document starts requiring the stylesheet, and the
markup is written so the unstyled case is a coherent page — the same picture
again, larger, with its caption and a working anchor.

**And the way it stays coherent is `display: none` and a reveal in the flow, not
an overlay.** `.planning/STATE.md:209` records what the other choice costs: in
the `weide` theme a positioned submenu counted toward the scroll width even
while hidden, and made *every page of the site* scroll sideways without anyone
opening the menu. Measured in headless Chrome at three widths before it was
believed. A gallery is on more pages than a submenu.

**The index, and it is two `range` statements and two signatures.**
`render.go:68` becomes `for i, blk := range blocks`, and `i` is passed to
`renderOwn` and `renderOne`. Both signatures gain an `at int` parameter, placed
after the builder. `renderOwn` does not use it today; give it the parameter
anyway and say why in one line — a reviewer reading one arm and not the other
should not have to work out whether the asymmetry means something. Both callers
of `Render` — `internal/admin/page_blocks.go:80` and
`internal/bundle/import.go:694` — call `Render` and not the unexported arms, so
neither changes.

**The one thing that must be written down rather than discovered: the id is
minted at save.** Block HTML is rendered once, on save, and stored in
`pages.content_html` (`page_blocks.go:74-81` says so in its own comment). So a
fragment id is frozen until the next save of that page, and reordering blocks on
a later save re-mints it — an old bookmark to a large view can land on a
different picture. That is acceptable for a bookmark into the middle of a photo
grid and it is not acceptable to leave a reader to find out. Put the sentence in
the doc comment above the id-minting line.

**The id itself.** `hc-b{at+1}-p{j+1}`, minted inside the gallery arm only, from
the block position and the item's own loop index. The `hc-` prefix is not
decoration: a heading in a text block on the same page can carry an id the
Markdown renderer derived from its words, and an unprefixed `b1-p1` is a
collision waiting for the one page that has a heading spelled that way.

**`GalleryItems`, exported, because GAL-07 says one mechanism.** Signature:

    func GalleryItems(at int, items []Item, look Lookup, t func(string) string) string

inner HTML — everything between the opening and closing `<div class="hc-block
hc-galerie …">`. The gallery arm of `renderOne` calls it; plan 11-05's album
expansion calls the same function with the items it loaded from the database.
Two renderers would be two places to get the fragment ids and the control links
wrong, and the album is the case where nobody would notice.

A doc comment in the voice `internal/admin/media_crop.go:14-24` uses for its own

The tile keeps everything it has today — the `<figure class="hc-galerie__bild">`,

The large view is a `<figure class="hc-galerie__gross" id="hc-b1-p2"

The three controls, and each is an ordinary `<a>`:

- previous — `href="#hc-b{at+1}-p{j}"`, **omitted entirely on the first

- next — `href="#hc-b{at+1}-p{j+2}"`, **omitted entirely on the last**. No

next task's stylesheet cannot rescue: no wrapper element whose only purpose is

specification until today did not link the stylesheet at all.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| an editor's caption and alt text → the rendered gallery HTML | Typed into an admin form, written into `pages.content_html`, served to every visitor. |
| a fragment in the URL → the page's `:target` state | The visitor controls the fragment. Nothing on the server reads it, and nothing must depend on it being one of ours. |
| `internal/block` → every page of every website | Block HTML is rendered once and stored. A defect here is baked into every page saved after it and is not fixed by a deploy. |
| an uploaded theme → the block markup | A theme may override every rule in `bausteine.css`, and after this plan it may also fail to link it. |
