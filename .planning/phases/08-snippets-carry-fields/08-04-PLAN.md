<objective>
Half the phase's effort, and almost none of its new code.

The snippet **value** form is the piece with no direct analog on a snippet
screen — but every part of it exists in the page editor. `fieldsFromRequest`
already parses `feld_*` and `gruppe.*` names including multi-values and row
buttons. `fieldViews` → `viewOf` → `oneView` already build the controls in Go
rather than in a template, for the reason its own comment gives: which input a
kind needs is a decision with eight branches, and eight branches in a template is
where a missing `name` attribute hides until somebody notices their entry never
saved. `field_top.html` and `field_input.html` already render them. `field.Clean`
and `field.CheckAll` already validate them.

So this plan is composition, and its discipline is to compose rather than to
re-implement. Phase 7 shipped a critical because a second place minted a form
name; the same shape here would be a second parser or a second control-builder.
There is one of each and this screen uses it.

The rendering pipeline is not touched at all. `page.RenderMarkdown` stays exactly
where it is, doing exactly what it does, which is how SNIP-03 is met by reuse
rather than by a second chain that must be tested against the first.

This plan also closes the Phase 7 security item **T-07-26**, which named
`field.Hidden` as dropping hidden values on save when `Hidden` is called on no
save path. It is closed by correcting the claim rather than by building the
mechanism, and the reason is written down.

Purpose: SNIP-01's filling half, SNIP-03's sanitisation, SNIP-05's untouched body.
Output: a snippet form that carries fields, and the tests that hold it.
</objective>

   snippet value form is not, and a flash loses what was typed.
5. `field.Clean(defs, values.Fields)`, then `field.Encode`, then

**T-07-26 — decided here, and the decision is to correct the wording.**

`07-SECURITY.md:82-93` records that the claimed mitigation names `field.Hidden`
as dropping hidden values on save, and that `Hidden` is called on no save path;
`field.Clean`, which *is* the save path, deliberately keeps a hidden field's value
(`field.go:568-573`: „Ein Feld, dessen Bedingung nicht erfüllt ist, behält seinen
Wert"). This plan is the first thing since Phase 7 to touch `Clean`'s callers, so
it is where the item is settled.

**Build nothing.** Amend the entry instead. The reasons, all three to be written
into the amended entry:

- Dropping hidden values on save would silently discard an operator's typed text
  the moment a condition flips — the data loss this project avoids everywhere
  else, and the exact opposite of the deliberate behaviour `Clean`'s comment
  records.
- A hidden field's value is not privileged data. It is the operator's own text on
  a page or a snippet of a website they already administer; there is no
  confidentiality boundary for it to cross.
- What actually protects is server-side validation: `field.CheckAll` runs over the
  definitions the server loaded, not over what the form claimed, so a value
  submitted for a field that does not exist is never stored, and a value that
  fails its kind's check is refused.

Rewrite the T-07-26 entry to state the real mitigation in those terms, mark it
closed, and strike it from the outstanding-items list at `:202-206`. Do not change
any other entry in that document, and do not change `field.Hidden`, `field.Clean`
or `field.CheckAll`.
