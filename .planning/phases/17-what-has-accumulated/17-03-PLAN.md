# 17-03 — The two limitations that were written down instead of fixed

Closes GAP-01 and GAP-02, and with them the last of phase 17.

---

## §1 Why these two are one plan

They have nothing in common technically. One is a bundle losing a field value,
the other is a marker expanded in the wrong place in a document. What they share
is their history: **both were measured, both were understood, and both were
written into a comment rather than fixed** — one in v2.0's deferred items, one
in the Phase 11 security audit as UF-1. Then they sat.

That is the shape 17-00 went looking for. A comment that says "this is broken
and here is why we are not fixing it" is honest the day it is written and turns
into furniture the day after. The ledger counts windows; neither of these was in
it; so nothing counted them. The requirement is therefore written with an "or":
**fixed, or an entry with a reason a reader can check.** Both turned out to be
fixable in an afternoon, which is the usual outcome and the reason the phase
exists.

## §2 GAP-01 — a snippet's picture did not survive a bundle

### What was wrong

The value of an image field is a media id, of a reference field a page id, of a
term field a slug. On the **page** path those are translated on the way out into
a file name and an address, and back on the way in into the ids of the machine
that is receiving (`exportFieldValues` / `translateIn`). On the **snippet** path
they went out raw and came in raw.

So after a move between machines the snippet carried a number belonging to
another website's rows. `fieldImages` and `fieldRefs` refuse such an id when the
snippet is rendered, so the field arrived and the picture did not — while the
report said the snippet had been created. A warning named the fields, and it
named them as a limitation rather than as a loss.

### What was done

The same translation, on the same three maps:

- `exportPages` now returns `slugByID`, and `exportSnippets` runs after it and
  takes `mediaByID, slugByID, nameBySlug`. The ordering is not incidental and is
  written down where it is relied on.
- `importPages` now returns the `pageIndex` it built, and `importSnippets` runs
  after it. A snippet's reference names a page **of this same bundle**, so the
  index has to exist before the snippet is written.
- `cleanSnippetValues` calls `translateIn`, including into a group's rows — a
  snippet has its own form, so a group is a row of it.
- A reference resolves in the **main language** (`pages.in("")`). A snippet is
  not per-language, so a reference in one names the page as the main language
  spells it. Stated at the call site, because `pageIndex.in` takes a language
  and this is the one place where the right answer is not obvious.

### What the operator is told now

Two messages where there was one, because there are two remedies:

- a value that **breaks its field's rules** has to be corrected;
- a value that **names a file or a page this archive does not carry** has to be
  chosen again here.

The old "points at ids of the installation the archive came from" warning is
gone, and so is `installationBoundValues`. An archive written before v2.4 still
carries raw ids: they resolve to nothing, so they are dropped rather than stored
as a foreign id, and the drop is reported under the second message.

### How it is held

`TestASnippetsPictureAndReferenceSurviveTheRoundTrip` seeds a site, gives a
snippet an image field, a reference field and a group with an image sub-field,
exports, imports, and asserts **the copy's ids** — not merely non-empty. It
first checks that copy and original do not share an id, so a version that copied
the number across cannot pass by coincidence. Driven red against the old
pass-through: it reported `logo = "1", want "2"` and `mehr = "1", want "3"`.

`TestASnippetsRawIdFromAnOldArchiveIsDroppedAndReported` is the renamed and
rewritten former `TestASnippetsImageValueIsReportedOnImport`. It now says what
it means: an archive from before v2.4, a raw id, dropped rather than kept, and
reported as unfindable rather than as rule-breaking.

## §3 GAP-02 — a marker expanded where it was not text

### What was wrong

`ReplaceAlbumMarkers` is a regular expression over the whole document. That is
fast, simple, and blind to where the match sits. The Phase 11 audit measured
what that costs (UF-1, 2026-09-08): nothing stops an editor typing the marker
into a text block, goldmark passes it through, and bluemonday keeps an `href`
that contains no space —

```
in : <a href="/x?q=[[album:sommer-2025:1]]">klick</a>
out: <p><a href="/x?q=[[album:sommer-2025:1]]" rel="nofollow">klick</a></p>
```

— so the marker reaches delivery inside an **attribute value**, and the
gallery's first quotation mark ends the attribute. The audit tried to make that
reach further and could not: everything after the break is renderer-generated,
alt text and captions are escaped, and `script-src 'self'` forbids inline script
regardless. Broken markup on one page, done by an authenticated editor to their
own website.

The comment said the fix was a change to the mechanism rather than a correction
to it. That was true. It is also not a reason.

### What was done

`internal/marker`, and one function: `OnlyInText(doc, patterns...)`. It removes
every match that is not character data — inside a tag, inside a comment, inside
the content of `<style>` or `<script>` — and nothing else. What is left is
exactly the set of matches a context-free replacement may safely expand.

Three decisions worth keeping:

1. **It tokenizes rather than parses.** `html.Parse` would build a tree and
   re-render it, which is a second pass over a body `media.MakeResponsive`
   already parses on the same route, and a re-render rewrites bytes this
   function has no business touching. The concatenation of the tokenizer's raw
   bytes **is** the input — that property is the whole foundation and has its
   own test, `TestTheTokensAreTheDocument`.
2. **It takes patterns, not prefixes.** Removing `prefix … ]]` would also remove
   `[[album:x]]`, which no expansion ever touched, so an operator's literal text
   would disappear. With the pattern, only what would have been expanded is
   removed.
3. **A document with nothing to remove comes back byte for byte** — which is
   every page this program writes itself, so the common case pays one tokenize
   and keeps its bytes.

It is wired into `ReplaceAlbumMarkers` **and** into `snippet.Expand`. The
snippet marker had the identical hole, because it is the same idea copied; it is
arguably the worse of the two, since a snippet's HTML is the operator's own
arbitrary markup. `ResolveWords` does **not** call it and does not need to: its
expansion goes through `html.EscapeString`, and escaped text is perfectly at
home in an attribute value. The package says so, so nobody adds the call later
out of symmetry.

### How it is held

`TestAnAlbumMarkerInAnAttributeDoesNotBreakTheMarkup` reads the result with a
real parser rather than matching strings — a substring check would pass on
exactly the broken output it exists to catch, because the gallery's markup is in
the document either way. What distinguishes them is whether the `<a>` still has
one `href` with the value the editor wrote. Driven red: `href = "/x?q=<div
class=", want "/x?q="`.

`TestASnippetMarkerInAnAttributeIsNotExpanded` is the same case on the snippet
side, red the same way.

Both tests also assert that a marker **in text** still expands, so the fix
cannot pass by removing too much.

## §4 What this changed that nobody asked for

Two things, and both are recorded rather than smuggled:

- **A second warning sentence** in the bundle report (four catalogues, `0 open,
  0 orphaned`). It is not a new string in the sense of new surface — it replaces
  one that is gone — but it is a different sentence and it says a different
  thing.
- **A new package**, `internal/marker`, which takes the exported-name count from
  986 to 987. It is used outside its own package by two others, which is the
  test `tools/surface` applies.

## §5 The ledger

UF-1 in `11-SECURITY.md` carries a dated closure note rather than a rewrite: the
audit is a record of what was true on 2026-09-08 and stays one. The note says
what closed it and names the two tests. `T-11-21`, whose row read "**aber siehe
UF-1**", no longer rests on a comment that says the opposite of what the code
does.
