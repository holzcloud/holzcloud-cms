<objective>
The half of this phase no test can hold, and the milestone's close-out.

Three things close phase 10 and, with it, v1.6.

**The first is a sign-on path driven in a browser with forward authentication
on.** Every property this phase built is invisible: nobody sees a new screen,
nobody clicks a new button, and the one thing that changes for a person is that
they are already in. That makes it exactly the kind of feature a test suite can
be entirely green about while the real thing does not work — a stray redirect, a
cookie that is not set, a session that is renewed and then read from the wrong
context. It has to be seen.

**The second is the same path with forward authentication off**, because
criterion 5 is not "the password path should still work" but "nothing about
signing in changed" — the password, the second factor, the recovery codes and the
command-line way back in. That is a claim about absence, and the only honest way
to check a claim about absence is to go and look.

**The third is the milestone.** Criterion 6 asks that `go run ./tools/i18n`
reports `0 offen, 0 verwaist` across everything v1.6 added and that **every field
kind from Phase 7, the snippet fields from Phase 8, both import paths from
Phase 9 and the sign-on path here** have each been driven once through the
running application. Phase 10 carries it because it is scheduled last, not
because it is related.

**Why this is one plan and not three.** The two sign-on passes belong together —
the second is only meaningful as a comparison against the first, run on the same
data in the same session. The sweep belongs with them because it is the same
running server, the same scratch directory and the same browser, and splitting it
would mean building the fixtures twice. What the split would buy is a shorter
plan; what it would cost is the thing `10-CONTEXT.md` warns about — a gate that
becomes a checklist nobody runs. This plan is long on purpose.

**And the ordering constraint that has caught this project three times.** The
browser pass runs **after** the code-review fix round. In phases 7, 8 and 9 the
verifier found user-visible changes landing after a pass had already been signed
off. A pass run early is a pass that has to be run again, and one that is not run
again is a signature on a screen nobody looked at.

Purpose: QUAL-02 and criterion 6, plus the browser halves of SSO-01, SSO-02,
SSO-08 and SSO-09.
Output: one summary carrying three numbered passes, a named screenshot per step,
every finding, and the phase's final arithmetic.
</objective>

**The stand-in for the identity provider.** There is no Authentik on this
machine, and installing one is not what criterion 1 asks for. What forward
authentication actually consumes is a set of headers from a trusted peer
carrying a shared secret — so the stand-in is a **tiny reverse proxy in front of
the CMS** that adds them, which is exactly what Caddy's `forward_auth` does after
the outpost answers. Write it as a short Go program in the session scratch
directory (`httputil.NewSingleHostReverseProxy`, twenty lines) that listens on
`127.0.0.1:9090`, sets `X-authentik-username`, `X-authentik-email`,
`X-authentik-name`, `X-authentik-groups` and `X-Holzcloud-Proxy-Secret` from its
own flags, and forwards to the CMS. Its identity is switchable between runs by
restarting it with different flags, which is what steps 6 and 7 need.

State plainly in the summary that this stands in for the outpost and what it does
**not** cover: the outpost's own authentication, the `copy_headers` behaviour
plan 10-08's Caddyfile addresses, and CVE-2026-30851 itself. Those belong to the
operator's verification in `DEPLOY.md`, which is where `10-CONTEXT.md` puts them.
A stand-in that is honest about its edges is worth more than one that is
described as the real thing.

**Setup.** Build the binary. Start it with `HOLZCLOUD_DATA_DIR` pointed at a
scratch directory under the session scratch path, `HOLZCLOUD_SSO_ENABLED=true`,
a secret, `HOLZCLOUD_SSO_ADMIN_GROUP=holzcloud-admins`,
`HOLZCLOUD_SSO_WEBSITE_GROUPS=redaktion-a=1,redaktion-b=2`,
`HOLZCLOUD_SSO_PROVISION=true` and `HOLZCLOUD_SSO_DEFAULT_WEBSITE=1`. Run
through first-run setup to create the initial administrator with a **password** —
that account is the control for task 2 — and create a second website so there is
one to be refused. Then start the stand-in proxy and drive the browser through it
with the Playwright MCP tools.

**One thing about criterion 2 that only becomes visible when it is run.** The
command is stated as "from a second machine, over IPv4 **and** IPv6". The server
now binds loopback by default (SSO-10), so run literally, from a second machine,

returned, and proves **nothing** about layers 1 to 3. It proves the listener.

can and does prove; the other half is the operator's verification in
`deploy/DEPLOY.md`. Saying so is worth more than a step that looks like it
covered it.
