<objective>
The fourth caller, and seven things that must not move.

`completeLogin` (`internal/admin/login.go:106`) is the single place a session
becomes signed in. It has three callers today — the password form at `:97`, the
second-factor path at `twofactor.go:118`, and first-run setup at `setup.go:121`
— and it is where the last-login stamp and the `auth.login_success` row are
written. A forward-auth path that put `user_id` into the session itself would
work perfectly and be **invisible in `/admin/protokoll`**, which is the one place
an operator looks when something changed and nobody admits to it. So it becomes
the fourth caller and nothing else.

Two traps sit inside this plan, and both are quiet.

**The first is session fixation.** `login.go:80` calls `sm.RenewToken` *before*
setting any value, with the reason in a comment. A middleware that signs somebody
in on the strength of a header without renewing the token hands the session to
whoever set the cookie first. `RenewToken` runs here in the same position and for
the same reason.

**The second is that e-mail is not an identity.** D-02 pins the identity to
`X-authentik-username`, and the account key has to be `users.email` because the
`users` schema is on the roadmap's deliberately-unchanged list and `email` is the
only unique key it has. That is workable, but SQLite's `COLLATE NOCASE`
(`00001:5`) folds **ASCII only**: `Müller@example.com` and `müller@example.com`
are two rows, two accounts and, in the worst case, two administrators. This plan
does not guess between them. An address carrying any byte above 0x7F is refused
with a named reason and falls through to the password form, and `DEPLOY.md` says
so in plan 10-08.

Purpose: SSO-01, and the half of SSO-09 that is proved by absence.
Output: one middleware, one session key, one line in `main.go`, and a gate for
each of the seven things the roadmap says must not change.
</objective>

**One new file**, `internal/admin/forwardauth.go`, holding one exported method
and two unexported helpers. It is a method on `*Handler` and not a free function
with dependencies passed in, for one reason that is not convenience:
`completeLogin` is unexported, and the roadmap requires the new path to go
through it. A free function would have to export `completeLogin` or reimplement
it, and reimplementing it is how the `/admin/protokoll` row goes missing.

    func (h *Handler) ForwardAuthSignIn(next http.Handler) http.Handler

The body, in this order, with a comment saying that the order is the design:

1. `if h.cfg == nil || !h.cfg.SSOEnabled { next; return }`. SSO-09's first line
   of defence and the cheapest one: with the switch off, nothing below runs.
2. `ident, ok := web.IdentityFromContext(r.Context())`; if not, `next` and
   return. **The identity comes from the context and never from a header** —
   plan 10-02 deleted the headers, so there is nothing to read even if somebody
   tried.
3. `if h.sm.GetInt64(r.Context(), auth.SessionKeyUserID) != 0 { next; return }`.
   A session that is already signed in is left exactly as it is. The comment says
   why this is not an optimisation: without it, every request would renew the
   token and write a `login_success` row, and `/admin/protokoll` would become
   one row per page view.
4. The address rule. `email := strings.ToLower(strings.TrimSpace(ident.Email))`.
   Refuse — `h.refuseSSO(r, ident, reason)` then `next` — when it is empty or
   when `isASCII(email)` is false. The comment on `isASCII` is the longest in the
   file and carries D-02 whole: `users.email` is `UNIQUE COLLATE NOCASE`
   (`00001:5`), SQLite's NOCASE folds ASCII only, Go's `ToLower` folds Unicode,
   and the two disagreeing means an address like `Müller@example.com` can match
   nothing while a second row for `müller@example.com` sits beside it. Refusing
   is the only answer that does not guess; matching by hand-rolled folding would
   be a second definition of identity standing beside the database's.
5. `u, err := h.users.GetByEmail(r.Context(), email)`. An error is
   `slog.Error` + `next` — a database that cannot answer must not turn into a
   sign-in. `u == nil` is `h.refuseSSO(...)` + `next`: **no account is created in
   this plan.** Provisioning is plan 10-04 and lands as a second branch here.
6. `if err := h.sm.RenewToken(r.Context()); err != nil { slog.Error; next; return }`
   — **before** anything is put in the session, with the same one-line comment
   `login.go:80` carries. A failed renew is a refused sign-in, not a sign-in with
   the old token.
7. `h.sm.Put(r.Context(), auth.SessionKeyViaSSO, true)` then
   `h.completeLogin(r, u.ID, u.Role, u.Email)`. The stored role and the **stored**
   address, not the header's: the activity row and the session must name the
   account, and the header only claimed to.
8. `next.ServeHTTP(w, r)`. The original request continues. It is not redirected:
   `scs`'s `LoadAndSave` commits the session at the end of the request and the
   values are already visible to `requireAuth` further in, so the person lands on
   the page they asked for rather than on a bounce through `/admin/`.

**`refuseSSO(r *http.Request, ident *web.Identity, reason string)`** — one
`slog.Warn` naming the username, the reason code and the client address from
`h.clientIP.ClientIP(r)`, and one `activity.Entry` with
`Action: activity.ActionAuthLoginFail`, `ActorEmail` set to the attempted
address and `EntityType: "user"` — the same shape `login.go:52-57` writes, and
for the same reason its comment gives: at a failed attempt there is no account,
and the attempted address is the thing one wants to recognise later. **A
refusal is never a 403.** SSO-02 is as much about that as about anything: the
way back in must not die with the proxy.

Do **not** reset or consult `h.loginThrottle` here. It keys on an address plus an
account and exists to slow password guessing; a forward-auth request carries no
password to guess, and feeding it would let a stranger at the identity provider
lock a real account out of the password form.

Write `forwardauth_test.go` against a real database with the package's existing
harness (`internal/admin/page_handler_test.go` is the pattern), one named English
subtest per line of the behaviour list. The session-token assertion is worth
writing carefully: capture the `Set-Cookie` value before and after and require
them to differ, because "RenewToken was called" is a proxy and "the token
changed" is the property.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the identity in the request context → a session | This is the moment a claim becomes an account. Everything before it is checking; everything after it is authorisation that already existed. |
| an e-mail address → a row in `users` | The database's own uniqueness rule is `COLLATE NOCASE`, which folds ASCII only. A matching rule wider than the database's is a matching rule that can find the wrong row. |
| the session cookie → the signed-in session | An attacker who fixed a session id before the sign-in owns the session after it, unless the token is rotated. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-15 | Spoofing | session fixation across the forward-auth sign-in | high | mitigate | `sm.RenewToken` before any `sm.Put`, in `login.go:80`'s position and with its comment. Proved by comparing the session cookie before and after the request rather than by asserting the call was made. |
| T-10-16 | Elevation of Privilege | a case-folding mismatch matching the wrong account | high | mitigate | The address is lowercased in Go and any byte above 0x7F is a named refusal. SQLite's NOCASE and Go's ToLower disagree above ASCII, and a rule wider than the database's can find a row the database considers distinct. Refused, never guessed; documented in `DEPLOY.md` by plan 10-08. |
| T-10-17 | Repudiation | an SSO sign-in invisible in the activity log | high | mitigate | `completeLogin` is the fourth caller and the only writer, so the `auth.login_success` row and the last-login stamp come from the same function the password path uses. Gated by counting its call sites at exactly 4. |
| T-10-18 | Repudiation | a refused SSO attempt leaving no trace | medium | mitigate | Every refusal writes one `auth.login_fail` row carrying the attempted address, the shape `login.go:52-57` already uses, plus a `slog.Warn` naming the reason code and the client address. |
| T-10-19 | Denial of Service | a refusal answering 403 instead of falling through | high | mitigate | The middleware writes no status on any path; gated by counting `http.Error`/`StatusForbidden`/`http.Redirect` in its body at 0. | T-10-20 | Denial of Service | forward auth feeding the login throttle | medium | mitigate | `loginThrottle` is deliberately not touched. | T-10-21 | Elevation of Privilege | an existing session overwritten by an identity | medium | mitigate | A request that already carries `SessionKeyUserID` is passed straight through.
