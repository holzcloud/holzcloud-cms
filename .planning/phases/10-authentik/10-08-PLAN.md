<objective>
The half of this phase that runs on somebody else's machine.

Two of the three requirements this plan carries cannot be satisfied by code
here at all. **SSO-11** is about a file an operator copies to
`/etc/caddy/Caddyfile`, and about a version number of a program this project does
not ship. **SSO-07's first half** is a sentence in `DEPLOY.md` — the admin half
was plan 10-06's two screens.

**CVE-2026-30851 is the reason SSO-11 exists and it is worth stating in full**,
because it is the kind of defect that reads as a footnote and behaves as a
bypass. Caddy's `forward_auth … { copy_headers X-Foo }` generates a
**conditional** set: `X-Foo` is written on the request when the auth service
returns one. It generates **no delete** for the client's own inbound `X-Foo`. So
whenever the outpost answers 200 *without* emitting that header — an anonymous
route, a user with no e-mail address, any header authentik chose not to send —
the client's own value reaches the backend verbatim. Affected v2.10.0 through
v2.11.1, fixed in v2.11.2, latent since November 2024, which means it is in
whatever Caddy a typical operator has from the stable apt repository right now.
The companion advisory GHSA-f59h-q822-g45g / CVE-2026-52845 is the underscore
variant, and it is why plan 10-02's strip normalises `_` to `-` before comparing.

Layer 2 already makes all of that a misconfiguration on somebody else's server
rather than a bypass here. This plan closes the other half: the shipped example
deletes the headers explicitly so the misconfiguration does not happen, and the
documentation names the version so an operator can tell whether they are exposed
by anything else they proxy.

**And the two facts that are genuinely the operator's.** `10-CONTEXT.md`
isolates them deliberately: whether their Authentik emits `X-authentik-username`
with the value they expect, and whether their Caddy is 2.11.2 or newer. Neither
is a planning blocker and neither can be looked up from here. They are written as
a verification the operator performs once, and criterion 2's one command is what
makes both checkable without this project having to know the answer.

Purpose: SSO-11 whole, and SSO-07's `DEPLOY.md` half.
Output: a Caddyfile somebody can copy, a deployment section somebody can follow,
and one paragraph in each of the two docs that already describe this
installation's security to a reader who is not deploying it.
</objective>

   ```
   curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' \
     -H 'X-authentik-email: stranger@example.com' \
     http://<server>:8080/admin/
   ```

   Run from a second machine, over IPv4 **and** over IPv6. The expected answer is
   `303 …/admin/login` — a **login form, not a dashboard**. Then the sentence
   that matters: **`Connection refused` is not a pass.** It means the port is not

   listener and says nothing about whether a header is believed. To test the
   header, the port has to answer: set `HOLZCLOUD_LISTEN=0.0.0.0` temporarily, run

   ASCII only, so `Müller@example.com` and `müller@example.com` are two rows and

   administrators. Refusing is the only answer that does not guess.
