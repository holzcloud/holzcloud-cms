<objective>
The single most likely way this milestone ships a real vulnerability, and the one
test that would catch it.

`internal/admin/handler.go:178` reads:

    return assigned == 0 || mine > 0

"No assignment means every website." That is correct — deliberately, with a
paragraph in `internal/user/rights.go:9-22` explaining that anything else would
have made the migration that introduced it lock everybody out. It is correct for
accounts an operator creates by hand. It **inverts** the moment accounts are
created automatically, because a freshly provisioned account has zero rows in
`user_websites` *by construction*. The first stranger who authenticates at the
identity provider becomes an editor of every website in the installation.

Every part of that looks correct in isolation, which is why it is dangerous.
`handler.go:178` is right. `Rights.MayUse` is right. `user.Store.Create` is
right. The bug lives only in the seam, and only once something creates accounts.

`handler.go:178` is **not** changed — changing it would lock out every existing
editor, which is the same failure arriving from the other side. Three things
stand in its place instead, and this plan is the third:

1. Provisioning is off by default (plan 10-01).
2. With it on, the process refuses to start without a default website
   (plan 10-01, twice: at load and against the database).
3. **The account is given that website in the same request that creates it, and
   a test asks the real authorisation function whether that worked.**

That third point is the one this plan is judged on, and it is judged by the
shape of the test rather than by the shape of the code. A test that counts rows
in `user_websites` proves that a row was inserted. It does not prove that the
function which authorises requests agrees, and the two are different claims —
`de4a1ce` in this repository is a cross-website hole of exactly that family,
found on 2026-09-06, where four handlers checked that an item belonged to its
menu and never that the menu belonged to the website. So the test calls
`NewWebsiteAccessLookup` itself.

Purpose: SSO-05's second half — "with it on, the service refuses to start until
it is told which website a new account belongs to" — as behaviour rather than as
configuration.
Output: one branch, one random hash, and the inversion proved closed.
</objective>
