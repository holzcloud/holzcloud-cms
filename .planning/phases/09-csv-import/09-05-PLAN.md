**1. One pass helper, so the two screens cannot describe different files.**

```
func (h *Handler) csvLauf(ctx context.Context, a *csvimport.Ablage, zu csvimport.Zuordnung,
	defs []field.Def, websiteID int64, schreiben bool, userID *int64) ([]csvimport.Urteil, bool, error)
```

One function walks the staged bytes once, in row order, and produces the
verdicts. `schreiben` is the **only** difference between the dry run and the
write, and the write is suppressed by not being reached rather than by a second
code path (D-22). The returned `bool` is `Abgeschnitten`.

Inside, in this order:

- `csv.Neu(bytes.NewReader(a.Daten))` — **the same staged bytes both times**,
  which is what makes IMP-05 true and is the property „re-submit the file" could
  not have had: under re-submission the operator could have picked a *different*
  file at the commit step and the dry run would have been describing the wrong
  one, silently (D-30). Say that in the function's doc comment.
- If `schreiben`: read every row once to collect `csvimport.Schlagwortnamen` and
  call `term.EnsureNames` **before** the row loop, then re-open the reader for the
  write pass. Two passes over bytes already in memory, and the order is
  `bundle/import.go:289-329`'s: every name normalised and ensured before any page
  is created, so a term field's value and the label it points at agree by
  construction. `EnsureNames` opens its own transaction and runs **once**, never
  inside the loop.
- The row loop: `PruefeZeile` when `schreiben` is false, `SchreibeZeile` when it
  is true. For the update arm, look the existing page up per row with
  `h.pages.GetPageBySlug`. **Per row and not from a map built before the loop** —
  a map goes stale during a 5000-row write, and IMP-02's concurrency resolution
  says the database is the arbiter rather than a pre-check in the importer. The
  read pool is separate from the write pool, so the lookups do not contend with
  the writes.
- Rows are processed **in file order** (IMP-04 ordering), so a file whose row 40
  duplicates row 4 gets the rename or the update in that order and the report
  reads the way the file does.
- Nothing else writes to the verdict slice (IMP-03 concurrency): one pass, in
  order, appended to once.

**No `BeginTx` in this file.** Every write the loop performs is a store call that
opens and closes its own transaction inside one row — `CreatePage` a single
autocommitted `INSERT`, `SetForPage` its own at `term/store.go:120`. The write
pool admits one connection (`db.go:28`, `_txlock=immediate`), so other requests,
admin and public, interleave **between** rows. That is the edge IMP-10 exists
for, and the gate is mechanical.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a mapping in a POST body → 5000 writes | The form decides what every row becomes; the body is not the form. |
| the write loop → the single write connection | `SetMaxOpenConns(1)`; anything held across rows blocks admin and public alike. |
| a repeated POST → a second import | A browser refresh re-sends the last POST. |
| a cell's text → the report screen | Operator-supplied strings are rendered back as part of a reason. |
| a verdict's reason → a translator's catalogue | A sentence built in Go never reaches one. |
