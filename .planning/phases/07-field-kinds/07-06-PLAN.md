<objective>
The button row, and the trap it sets.

FIELD-01 is small: a Choice rendered as radio buttons instead of a dropdown. The
options are the same, the stored value is the same, and a theme cannot tell the
difference — which is exactly why D-04 made it a display mode rather than a kind
of its own.

FIELD-08 is the reason this plan is last. Conditional fields are pure CSS. The
rule that hides a dependent field of a Choice is
`:has(> .form-group option[value=""]:checked)`, and a radio row has no
`<option>` for it to match. Without a new switch name and a matching rule,
**every field hanging on that Choice silently stops appearing and
disappearing** — no error, no log, just a form that quietly shows the wrong
fields.

Scheduling this last means the conditional mechanism is touched exactly once, as
a whole. That is also why the switch names for the other kinds this phase added
are decided here rather than scattered across four earlier plans: a Multiple
Choice, a Term field, a Range field and a Code field all became controllable when
their kinds were born, and each needs a switch name whose rule can actually fire.

Purpose: close FIELD-01 and FIELD-08 together, in one pass over the mechanism.
Output: a widened `switchOf`, one new stylesheet rule, the radio row, and a test
per controlling kind.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → page form (radio row) | The submitted value is one of the option strings, or the empty string. |
| stylesheet ↔ template | The conditional mechanism is a contract between a class name the server emits and a selector the stylesheet carries; nothing at runtime checks that the two agree. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-24 | Tampering | the conditional-field mechanism | high | mitigate | A switch name with no matching stylesheet rule leaves a dependent field permanently visible, so a field the author believes is hidden is shown and filled in. Task 3's test asserts, for every switch name the server can emit, both the class and the element the rule selects, and reads the stylesheet from disk to confirm the rule exists. This is the failure D-10 names and it is silent without the test. |
| T-07-25 | Tampering | values submitted by a radio row | medium | mitigate | The radio row submits an option string or the empty string, and `field.Check`'s `KindChoice` case already compares the value against the option list. A hand-crafted POST carrying a value that is not on the list is refused, exactly as it is for the dropdown. |
| T-07-26 | Information Disclosure | a hidden dependent field | medium | mitigate | A field hidden by the conditional rule is hidden by CSS only; its markup is in the page. That is already true of the mechanism as it stands and is unchanged here — the fields concerned belong to the same page form the editor is authorised to see, and `field.Hidden` drops their values server-side on save so a hidden field cannot smuggle a value in. |
| T-07-27 | Elevation of Privilege | the button row's markup | high | mitigate | No JavaScript is added: the row is radio inputs and a container class. An acceptance criterion greps the template for a script tag, an inline handler and a `javascript:` URL, matching the rule `internal/tmplmgr/script.go` already enforces for uploaded templates. |
| T-07-SC | Tampering | package-manager installs | low | accept | No `go get`, `npm`, `pip` or `cargo` install task exists in this phase — every symbol is Go standard library or already in `go.mod`. The package-legitimacy gate does not fire, and no legitimacy checkpoint is needed. |
</threat_model>
