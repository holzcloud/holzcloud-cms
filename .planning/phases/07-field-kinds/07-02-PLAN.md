<objective>
Ship migration `00046` and carry its four new columns through every layer that
reads a field definition: the store, the definition screen, and the bundle.

Three of this phase's kinds need a property the current table cannot hold. A
Choice needs to know whether it is a dropdown or a button row. A Multiple Choice
needs a cap on how many values may be picked. A Range needs a lower and an upper
bound. `REQUIREMENTS.md:293` already decided these get their own columns rather
than a reuse of the `auswahl` column, which is read one option per line — a line
that is not an option is exactly the ambiguity the encoding decision avoided.

The riskiest work here is mechanical, not conceptual: the `page_field_defs`
column list appears **seven times** in `internal/field/store.go`. Miss one and a
field loads with a silent zero value — a button row that renders as a dropdown,
a bound that is not enforced, with no error anywhere.

Purpose: give the three remaining kinds somewhere to keep their configuration,
before any of them is built.
Output: migration `00046`, four `Def` properties, seven corrected SQL sites, the
definition-screen controls, and the bundle round trip for all four.
</objective>

Choice needs to know whether it is a dropdown or a button row, a Multiple Choice
needs a cap on how many values may be picked, and a Range needs a lower and an

`darstellung` empty means the dropdown that exists today, so every field already
